# MORT 작업 사용자 분석

## 분석 범위

이 문서는 현재 Codex 대화에서 직접 확인한 요청과 저장소의 `AGENTS.md` 작업 규약만을 근거로 작성한다. 성격, 신원, 연령 같은 개인 특성은 추정하지 않으며, 새로운 대화에서 다른 선호가 확인되면 이 문서를 갱신한다.

## 주로 요구하는 것

1. **구현 위치와 연결 관계의 명확한 설명**
   - 기능이 어느 파일에 있고 어떤 생성기·빌드·Git hook과 연결되는지 정확한 경로로 확인하려 한다.
   - 단순 파일 목록보다 원본 데이터, 생성 과정, 결과물, 자동 실행 지점을 함께 파악하는 설명이 유용하다.

2. **코드와 문서의 동기화 상태를 눈으로 확인할 수 있는 장치**
   - 위키가 존재하는 것만으로 끝내기보다 실제 코드가 얼마나 반영됐는지 수치로 확인하려 한다.
   - 자동 생성 여부와 사람이 직접 검토·설명한 범위를 구분하는 투명한 지표가 적합하다.

3. **장기 유지보수 맥락을 보존한 점진적 변경**
   - 기존 설정 파일과 사용자 호환성을 깨뜨리지 않는 것을 우선한다.
   - 오래된 구조와 새로운 구조의 공존을 허용하며, 요청 범위를 넘어선 전면 리팩터링은 원하지 않는다.

4. **반복 작업의 자동화와 검증**
   - 문서 갱신을 수동 기억에만 맡기지 않고 빌드와 pre-commit 과정에 연결하는 방향을 선호한다.
   - 결과물 생성뿐 아니라 최신 상태 검사와 개인정보 검사 같은 안전장치도 중요하게 본다.

## 원하는 작업 방향

- 기존 동작과 호환성을 먼저 보존한다.
- 변경 범위는 요청한 기능에 집중한다.
- 주변 코드 스타일과 현재의 혼합 구조를 존중한다.
- 구현 결과는 파일 경로와 데이터 흐름으로 추적 가능하게 만든다.
- 문서는 코드에서 자동 수집할 부분과 사람이 판단해 기록할 부분을 구분한다.
- 완료 여부는 실행 가능한 검사나 수치로 확인한다.
- 생성 파일을 직접 수정하기보다 원본과 생성기를 수정한다.

## 소통 선호 추정

| 항목 | 선호 방향 | 확신도 | 근거 |
|---|---|---:|---|
| 응답 방식 | 결론과 정확한 위치를 먼저 제시 | 높음 | 위키 구현 위치를 직접 질문함 |
| 구현 보고 | 변경 파일과 자동화 연결 관계 포함 | 높음 | 원본·생성기·hook 위치 확인 흐름 |
| 변경 규모 | 필요한 범위만 수정 | 높음 | `AGENTS.md`의 범위 외 리팩터링 금지 |
| 문서 품질 | 코드와의 최신성·반영 범위를 계량화 | 높음 | 코드 반영률 표시 요청 |
| 질문 방식 | 발견 가능한 내용은 먼저 조사하고 진행 | 중간 | 구현 위치 조사 후 후속 기능 요청 |
| 설명 길이 | 간결하되 검증 근거는 생략하지 않음 | 중간 | 짧고 직접적인 한국어 요청 패턴 |

## Codex가 작업할 때 적용할 기준

1. 변경 전에 관련 위키와 실제 호출 지점을 확인한다.
2. 호환성에 묶인 enum 순서, 직렬화 키, `@KEY ` 설정 형식은 변경하지 않는다.
3. 거대 파일 분리나 라이브러리 통일은 별도 요청 없이는 수행하지 않는다.
4. 새 비즈니스 로직은 가능한 한 `Service/`, 새 모델은 `Model/`, DI 등록은 `Program.ConfigureServices`에 둔다.
5. `Resources/localize.csv`는 직접 수정하지 않는다.
6. 구현 방식이 바뀌면 위키 원본도 같은 작업에서 갱신한다.
7. 작업 마지막에 위키 생성기와 관련 검사를 실행하고 결과를 보고한다.

## 앞으로 확인하면 좋은 점

- 코드 반영률에서 자동 수집보다 사람의 검토 완료율을 더 중요한 완료 기준으로 볼지
- 변경 보고에 diff 요약, 테스트 결과, 화면 캡처 중 무엇을 우선할지
- 사용자 분석 문서를 대화마다 자동 갱신할지, 명시적인 요청이 있을 때만 갱신할지

이 항목들은 아직 대화 근거가 충분하지 않으므로 확정된 선호로 취급하지 않는다.
